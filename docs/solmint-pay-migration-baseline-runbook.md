## 1. Objective

The Production database is authoritative for the deployed schema. The repository must become deterministic without pretending that the historical remote migration SQL can be reconstructed from filenames.

The recovery therefore creates a canonical baseline from the exact schema-only Production snapshot, validates that baseline on disposable PostgreSQL, and only then repairs the Supabase migration ledger using the supported `supabase migration repair` command.

`migration repair` changes migration tracking metadata; it does not execute or revert the migration SQL. citeturn442423search0turn442423search2

## 2. Evidence frozen before repair

Production currently has 56 applied migration versions, ending at `20260826190853 category_default_media_gallery_rpc`. The complete list is retained in `docs/solmint-pay-supabase-production-migration-ledger-2026-09-03.txt`.

The schema-only Production capture is retained by its SHA-256 and was independently replayed/equivalence-checked before this recovery path was designed.

No Pay migration is currently recorded in Production.

## 3. Canonical baseline artifact

The baseline is generated by:

```bash
node scripts/solmint-pay/baseline-prepare.mjs /path/to/production-schema.sql
node scripts/solmint-pay/baseline-validate.mjs supabase/migrations/20260829090000_solmint_production_baseline.sql
```

The generator refuses a hash mismatch, overwrites, top-level data-import statements, or obvious credential material. It embeds the exact audited Production snapshot hash and explicit start/end markers.

The generated migration MUST be committed as `supabase/migrations/20260829090000_solmint_production_baseline.sql` before any Production history repair.

## 4. Active migration directory after baseline activation

The active migration directory must contain:

1. the canonical Production baseline at `20260829090000`;
2. the 47 Pay migrations beginning at `20260830000050`;
3. no reconstructed historical placeholders.

The 14 legacy short-name site migration files are not evidence of exact remote migration identity and must be preserved outside the active migration directory under a clearly named archive path before baseline activation. Their Git blobs must remain unchanged for forensic traceability.

Archiving is a repository operation. It is not a database rollback.

## 5. Disposable validation gate

Before any Production repair, validate all of the following on disposable infrastructure:

- generated baseline hash and markers pass;
- baseline SQL executes successfully;
- baseline schema is equivalent to the captured Production schema under the established comparator;
- all 47 Pay migrations execute after the baseline;
- non-Pay definitions remain unchanged by the Pay chain;
- migration ordering contains no duplicate or regressive version;
- local migration tooling reports the expected pending/applied relationship.

Use `supabase db push --dry-run` as a preview and `supabase migration list` to compare local and remote history. These commands do not replace the schema-equivalence tests. citeturn442423search0

## 6. Production repair guard

The only supported Production history mutation in this runbook is:

```bash
SUPABASE_PROJECT_REF=nvopkbiedorfshwbmyhn \
SUPABASE_ACCESS_TOKEN='...' \
CONFIRM_PROD_MIGRATION_REPAIR=I_UNDERSTAND_METADATA_ONLY \
./scripts/solmint-pay/migration-repair.sh apply
```

The script refuses to run unless:

- the Production ledger manifest exists;
- the ledger contains exactly 56 versions and the expected manifest SHA;
- the canonical baseline exists and passes the validator;
- the exact Production project ref is supplied;
- an access token is supplied;
- the explicit metadata-only confirmation is supplied;
- no previous repair state file exists.

The forward operation is intentionally conservative: each of the 56 historical versions is marked `reverted`, then the canonical baseline `20260829090000` is marked `applied`.

No direct SQL write to `supabase_migrations.schema_migrations` is permitted.

## 7. Immediate post-repair validation

Immediately after a successful repair, independently verify:

```bash
supabase migration list --project-ref nvopkbiedorfshwbmyhn
supabase db push --project-ref nvopkbiedorfshwbmyhn --dry-run
```

Then re-check the Production schema for:

- no Pay objects;
- no unexpected relation/column/constraint/index/function/policy/trigger/grant changes;
- unchanged Production schema evidence as compared with the frozen capture.

A successful history repair is NOT permission to apply Pay migrations. Pay application remains a separate release-gated change.

## 8. Rollback semantics

Before the first Pay migration is applied, history rollback is possible with:

```bash
SUPABASE_PROJECT_REF=nvopkbiedorfshwbmyhn \
SUPABASE_ACCESS_TOKEN='...' \
CONFIRM_PROD_MIGRATION_REPAIR=I_UNDERSTAND_METADATA_ONLY \
./scripts/solmint-pay/migration-repair.sh rollback
```

This marks the canonical baseline reverted and restores the original 56 historical versions as `applied`, using the frozen ledger manifest.

This is a **metadata rollback only**. It does not undo schema SQL because `migration repair` never executes schema changes.

After any future Pay schema has actually been applied, metadata rollback alone is NOT a database rollback. Recovery then requires the normal database backup/restore strategy or an explicitly reviewed compensating migration. Never pretend that changing migration history reverses schema state. citeturn442423search0turn442423search2

## 9. Operational requirements for the repair window

Production repair requires a maintenance/change window with:

- `/pay` still disabled;
- no Pay migration executing concurrently;
- a fresh Production schema/ledger recheck immediately before repair;
- the Production schema snapshot and ledger manifest retained;
- the repair state file retained until post-repair validation completes;
- an operator watching the CLI output and stopping on the first unexpected result.

## 10. Explicit prohibitions

Do not rename legacy migrations to the 14-digit remote versions.

Do not create empty historical migration stubs.

Do not hand-edit the canonical baseline after generation.

Do not write directly to `supabase_migrations.schema_migrations`.

Do not run Pay migrations merely because the baseline is marked `applied`.

Do not report PASS when `migration list`, `db push --dry-run`, schema equivalence, or Production revalidation is incomplete.
